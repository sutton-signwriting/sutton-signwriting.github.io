From a clear outcome to a verified change.

The Sutton SignWriting Back Office uses a project-rooted Codex workflow: establish context, make bounded changes, verify the result, and cross the publication boundary deliberately.

Follow the working loop OpenAI Codex CLI guide
Acceptance rule A change is not complete because an agent says it is. Inspect the evidence.

Purpose

Keep the work close to the project that owns it.

Start in the narrowest project directory that owns the outcome. This gives Codex the right source files, version-control history, project instructions, and verification commands without pulling unrelated work into the conversation.

Steve is the hinge: Front prepares; Back implements; nothing is approved until he says so. Use one clear outcome per conversation; unrelated goals deserve separate sessions and separate review.

Working loop

Move through six evidence-producing steps.

01

Enter

Open the project that owns the outcome and inspect its instructions.

02

State

Describe the desired result, constraints, and important acceptance checks.

03

Inspect

Read the relevant code, documentation, history, and current working state.

04

Change

Make the smallest coherent edit that fully addresses the outcome.

05

Verify

Run proportionate checks and inspect browser-visible or runtime behavior.

06

Review

Examine the diff, preserve unrelated work, and record a clear handoff.

Office handoff

What crosses the boundary

Packet in

The ask, constraints, Stewardship vetoes, and acceptance conditions arrive as one specifically authorized packet.

Verified result out

Implementation returns evidence of the result or a bounded handoff with remaining gaps. Steve authorizes each crossing.

Durable context

Decisions

Tasks

Safety and review

Permission, scope, and verification are different questions.

Before changing

  • Confirm that the request authorizes the intended mutation
  • Protect credentials, personal records, and unpublished material
  • Check for unrelated or concurrent work before editing

Before declaring success

  • Run syntax, build, test, health, and behavior checks appropriate to the risk
  • Review the resulting diff and repository status
  • Separate verified facts from inferences and remaining uncertainty

Multiple sessions

Parallel work needs isolation.

Several read-only conversations can safely inspect the same project. Concurrent writers should use separate branches or Git worktrees so their changes, tests, and commits remain reviewable.

Delegate only bounded work that can proceed independently. The main conversation remains responsible for integration, verification, and the final result.

Publication boundary

Private development becomes public only through an explicit, reviewed release.
